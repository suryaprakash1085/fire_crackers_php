## 1. Stack found (read before changing anything)
- **Plain PHP 8.1+** with a small custom MVC (no Laravel/Symfony): `app/Core` (Router, DB/PDO, Auth, Migrator), `app/Controllers`, `app/Services`, `app/Views`, routes in `app/routes.php`, front controller `public/index.php`.
- **MySQL/MariaDB via PDO** (prepared statements, `ATTR_EMULATE_PREPARES=false`). Migrations: `database/migrations/*.sql` via `php bin/console migrate`.
- **PDF: hand-written PDF writer** (`app/Services/PdfInvoice.php`) – *not* TCPDF/Dompdf. **XLSX: in-house writer** (`app/Services/Xlsx.php`, uses PHP `ZipArchive`). **No Composer** (`vendor/` does not exist; PHPMailer is bundled in `app/Vendor`).
- **Cart storage: PHP session** (`$_SESSION['cart'] = [product_id => qty]`), summarised by `CartService`.
- Company details are **not a table**: they are key/value rows in `site_settings` (so the requested `ALTER TABLE … ADD COLUMN` became setting keys, see §3).
- Note: `suriyade_fc2__1_.sql` was not in the zip; I used `database/schema.sql`.

## 5. What I found / how each task was solved
**Task 1 – root cause (reproduced):** with the default `min_order_amount` = ₹3,000, a fully filled form with a smaller cart silently came back showing only *"Please fix the highlighted fields."* with **nothing highlighted** – no order. Fixes: the minimum-order rule is now shown on the checkout page up front (with the exact amount still missing), the Place Order button is disabled with that reason, and the message is always shown (also together with field errors). **If you do not want a minimum, set "Minimum order amount" to 0 on the Company page.**
Also fixed: if stock/availability changed after the cart was built, `summary()` used to silently trim/drop lines and the customer got an order for *fewer items than they saw* – now the order is not placed and they return to the cart with an explanation. The confirmation email is now sent *after* the redirect (`after_response()`), so a slow/broken SMTP can never delay or break an order. Mobile `09876543210` is accepted, address minimum is 5 chars (was 10), checkout attempt limit 15→40/h per IP, submit button recovers after back/forward navigation, first error is scrolled into view. Already correct and kept: DB transaction + rollback (proved with an injected failure), stock re-check with row locks, unique order number, CSRF token, idempotency token (double submit = one order). New: customer **Download Invoice (PDF)** on the confirmed page and on Track (allowed only for this browser's just-placed or reference+mobile-verified order).
**Task 2 – causes:** typed values (0, blank, 2.5, -4, above stock) were shown but silently coerced; the corner "+" quick-add always added 1 whatever the card showed; "−" at 1 sent 0 (deleted the line); stale cart responses could overwrite newer ones and the JSON API had no `Cache-Control`. Now: `FC.qtyOf()` forces a whole number 1..min(stock, max per item) and writes it back; Add sends exactly that; the box returns to 1 after a successful add; server rejects non-integers/0/negatives with 422 (`parse_qty`), adds to the existing quantity (capped at stock), `/api/cart/update` refuses 0; badge, line total, subtotal all re-render from the one server cart; API responses are `no-store`; out-of-stock cards have no quantity box and a disabled button.
**Task 3:** `Download Excel` button (next to the old *Export CSV*, which still works) → `/admin/orders/export-excel`, honours search/status/source/date filters, real `.xlsx`, `orders_YYYY-MM-DD.xlsx`, exact column list requested, bold header, auto widths, amounts as numbers (`#,##0.00`), real Excel date, mobile/pincode as text. Login required (same guard as the Orders page). If PHP `zip` is missing it falls back to UTF-8-BOM CSV.
**Task 4:** SKU = category prefix + number, generated in `SkuService` **inside the save transaction** with `SELECT … FOR UPDATE` on the category row; unique indexes are the safety net. Existing categories learn their prefix from existing SKUs (FP101-103 → next FP104; SP204, GC303 …), new categories get a prefix from the name (Fountains → FO…). Read-only on edit, never changes; posted `sku`/`selling_price` are ignored. Selling price input removed; read-only live preview (JS) + same rule on the server; `selling_price` and `discount_percent` are stored. **Approach for the discount:** prices were already calculated *live* from the company discount everywhere on the storefront (kept), and I added the **"Apply discount to all products"** button (with confirmation) that re-writes the stored columns – so both ways are covered. Excel *import* still requires a SKU column (unchanged).
**Task 5:** Logo upload (type detected from file *content*, 2 MB, random name in `public/uploads/company/`, GD re-encode strips metadata, **SVG is parsed and sanitised** – scripts/handlers/external links removed, ENTITY rejected, folder `.htaccess` serves SVG sandboxed), preview, Remove, old file deleted on replace/remove. Used in site header, admin header, HTML invoice preview and the PDF (falls back to the legacy "Logo" from App Customization, then the icon). **GPay / UPI ID** validated with your regex (the existing `company_upi_id` key is reused – one source of truth). **Default discount %** (0-90) = existing `company_discount_percent`.
**Task 6:** QR is drawn as vector squares from the UPI link `upi://pay?pa=…&pn=<rawurlencode>&am=<total 2dp>&cu=INR&tn=<rawurlencode "Order REF">`. Verified: the encoder is bit-identical to the `qrcode` reference library for all sizes tested (v1-v40 limits) and the QR **scanned from the rendered PDF decodes to the exact link**. "SCAN TO PAY" box (QR 32.5 mm, UPI ID, "Pay Rs. … via GPay / PhonePe / Paytm") under the totals; paid → green **PAID** stamp, no QR; empty/invalid UPI → section silently hidden. Logo at the top of the invoice (SVG logos fall back to the name, because the PDF writer can only embed raster images).

## 7. Assumptions
- Company settings = `site_settings` keys (no company table); "Default discount %" = the existing `company_discount_percent`.
- QR is hidden for cancelled/refunded orders as well as paid ones; no `tr=` parameter (personal UPI IDs can reject it); `tn` carries the order number.
- The PDF base font has no ₹ glyph, so the invoice prints "Rs." (as before). Tamil text is not supported by the built-in PDF font (as before).
- Excel columns are exactly the list requested; delivery charge is not a column (Subtotal − Discount + Delivery = Total).
- Any logged-in admin-panel user (admin or staff, as on the Orders page today) can download the Excel; tell me if it should be admins only.
- Tests were run on PHP 8.3 + MariaDB 10.11 here; I could not test in a real browser, so the card/cart JS was tested with jsdom against your real rendered page, and the PDF by rendering it and decoding the QR.
